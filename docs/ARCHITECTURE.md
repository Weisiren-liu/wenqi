## 1. 定位

**产品定位**：自动文档格式处理工具。用户描述自己的文档格式要求，工具把任意 Word 文档批量套用成该格式。

**主页面主角**：自定义文档格式。
**传统固定格式**（公文、学术论文、法律文书）降为**可选项**，是"内置好的现成答案"，不是产品主体。

这个定位与现有代码能力的落差，集中在两处：

| 维度 | 现状 | 目标 |
|---|---|---|
| 页面主角 | 「智能一键处理」模式卡片 | 「自定义文档格式」 |
| 格式选择 | 排在页面最下方、仅智能模式可用 | 与文件选择同级，三种处理方式都可见 |
| 内置格式 | 与"自定义"并列成一组卡片 | 降为次级可选项 |
| 预设来源 | 三套互不协调（见 2.1） | 单一注册表 |

## 2. 现状盘点（已逐行核实）

### 2.1 核心问题：三套互不相干的"预设"体系

这是本次改造必须先解决的**结构性冲突**。代码里同时存在三套独立的预设概念，各自有存储、读取和判定逻辑：

```
① formatter.PRESETS          硬编码在 scripts/formatter.py:317
   {'official','academic','legal'} —— 只读，不在用户配置里
   format_document() 走 else 分支直接取用

② config['presets']          用户配置里的自定义预设列表
   每项带 uuid / name / is_builtin，由 CustomSettingsDialog 增删改
   format_document() 走 preset_name == 'custom' 分支，经 load_custom_preset() 读取

③ 主页面预设卡片             docformat_gui.py:4061 硬编码三个元组
   ('official','GB/T 公文标准') 等 + ⚙️ 自定义卡片
   点击「自定义」不选中格式，而是打开设置弹窗
```

**造成的实际问题**：

- 主页面能选的格式，和 `CustomSettingsDialog` 下拉框里能选的预设，**是两批完全不同的东西**。用户在设置里新建的"我的格式A"在主页面根本看不到。
- `BUILTIN_PRESET_IDS = ('official','academic','legal')`（`docformat_gui.py:554`）**定义后从未被任何代码引用**。
- `is_builtin` 标志被写入 6 处（563/587/676/702/1383/1432/1579/2151），但只在 `_refresh_preset_list()`（1359 行）里被读一次，用于把内置项从下拉框过滤掉。
- `format_document()` 内部用 `if preset_name == 'custom'` 这种字符串魔法值分流，内置预设与用户预设走两条独立代码路径（`formatter.py:1770-1788`）。

> 结论：原作者已经预备了统一预设的能力（`is_builtin` / `BUILTIN_PRESET_IDS`），但没走完。本次改造是**顺着原设计把它补完**，而非推倒重来。

### 2.2 配置路径：双份解析逻辑，当前结果一致

| 位置 | 解析方式 |
|---|---|
| GUI `_get_config_dir()`（389 行） | macOS → `~/Library/Application Support/DocFormatter/`；Win → `%APPDATA%/DocFormatter/`；Linux → `$XDG_CONFIG_HOME/DocFormatter/`；不可写时退回 exe 同目录 |
| formatter `load_custom_preset()`（272 行） | 完全独立地重新实现了一遍同样的平台判断 |
| formatter 额外逻辑（283 行） | 若上述文件不存在，**回退读仓库根目录的 `custom_settings.json`** |

当前两侧路径恰好一致，但这是**巧合性的**：任何一侧单独修改就会分叉。且 `README_DEV.md` 里"Windows/Linux 打包发布版：exe 同目录"的说法与代码（`%APPDATA%`）**已经不一致**，是过时文档。

**改造要求**：配置解析必须收敛为单一实现。建议由 `scripts/formatter.py` 暴露 `get_config_dir()`，GUI 反过来 import 它（当前依赖方向是 GUI → formatter，不新增反向依赖）。

### 2.3 可自定义的格式项

`DEFAULT_CUSTOM_SETTINGS`（471 行）出厂值**本身就是公文参数**（页边距 3.7/3.5/2.8/2.6 cm、仿宋_GB2312 三号、行距 28 磅）。这意味着把「自定义」提为主角后，**默认观感不变**，不构成体验退化。

| 类别 | 字段 |
|---|---|
| 页面 | `page.{top,bottom,left,right}`（cm） |
| 元素 ×9 | `title` `recipient` `heading1-4` `body` `signature` `date` `attachment` `closing` |
| 每元素参数 | `font_cn` `font_en` `size` `bold` `align` `indent` `line_spacing` `space_before` `space_after` |
| 表格 | `table.{font_cn,font_en,size,bold,line_spacing,first_line_indent,header_bold,smart_align}` |
| 页码 | `page_number` `_font` `_size` `_style` `_position` `_offset_mm` `replace_existing_page_number` |
| 行为开关 | `space_handling` `first_line_bold` `bold_serial` `deep_clean` `split_heading_at_punct` |

**语义模型是公文专用的**：主送机关、落款、附件、特此说明这些元素，在学术论文或商业报告里没有对应物。本轮明确**不动**，但下一轮泛化时，这是主要改造点（见第 8 节）。

### 2.4 处理模式与格式的关系

`_on_mode_change()`（4428 行）中 `enabled = mode in ('smart',)` —— 格式预设**只对智能一键处理生效**，选诊断或标点修复时预设卡片被置灰。

这是当前信息架构里最需要反转的一点：格式选择被表达为"某个模式的子参数"。按新定位，格式是全流程的主轴，诊断模式也应该能"按指定格式给文档体检"。

## 3. 目标架构

### 3.1 单一预设注册表

把三套体系合并为一个扁平注册表：内置预设作为**只读条目**参与注册表，与用户预设并列，唯一区别是能否编辑。

```
                    ┌─────────────────────────────────────┐
                    │        预设注册表（唯一真相源）        │
                    ├─────────────────────────────────────┤
  只读内置  ──────▶ │ official   公文格式    （只读）        │
                    │ academic   学术论文    （只读）        │
                    │ legal      法律文书    （只读）        │
                    ├─────────────────────────────────────┤
  用户预设  ──────▶ │ <uuid>     我的格式A   （可编辑/删除）  │
                    │ <uuid>     我的格式B   （可编辑/删除）  │
                    └─────────────────────────────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      主页面格式选择          设置弹窗预设管理        format_document()
```

**关键设计决定：**

1. **内置预设不再从 `formatter.PRESETS` 直接进 UI**，而是在加载配置时**注入**到注册表，带上 `is_builtin: True` 与稳定的 `id`（沿用 `'official'` 等字符串，与 `PRESETS` 的 key 一致，保持向下兼容）。
2. **编辑内置预设 = 活链接 + 覆盖值，不复制**。见 3.3 节的数据流 —— 这是原型阶段最终确定的模型，推翻了本节最初"自动另存为副本"的想法。
3. **`format_document()` 的取值改为统一入参**：调用方始终传入完整 preset dict，删掉 `preset_name == 'custom'` 这个分支。入参保留 `preset_name` 仅为向后兼容旧调用方（现有测试大量使用 `format_document(..., 'official')`）。
4. **`BUILTIN_PRESET_IDS` 与 `is_builtin` 真正投入使用**，不再是死代码。

### 3.2 配置 schema 演进

```jsonc
{
  "schema_version": 3,              // 2 → 3，触发现有迁移链
  "active_preset_id": "official",   // 允许指向内置 id（此前只能指向用户 uuid）
  "page_number_config_version": 1,
  "presets": [
    // 内置项由加载时注入；此处只持久化用户项，避免用户配置被内置定义污染
    { "id": "<uuid>", "name": "我的格式A", "is_builtin": false, "...": "..." }
  ],
  "preset_overrides": {}          // 覆盖值：{预设 id: {键: {字段: 值}}}，见第 9 节（已定稿）
}
```

**为什么内置项不写进 `presets`**：内置定义随代码演进而变（新版本可能调整公文参数）。若持久化到用户配置，升级后会与代码里的新定义冲突，需要额外的版本比对逻辑。加载时注入、持久化时过滤，天然免疫这个问题。

`active_preset_id` 允许指向内置 id 是关键改动 —— 当前 `load_custom_settings()`（682 行）会校验 `active_preset_id` 是否存在于 `presets` 列表中，不存在就重置为第一个。注入内置项后，指向 `'official'` 也能通过校验。

#### 格式编辑内联 + 预设作起点

**格式编辑不再走弹窗**，直接内联在主页面。左侧一列预设作为**起点**，点击即把参数装载进右侧参数表。

参数表一行一个元素（主标题 / 主送机关 / 一~四级标题 / 正文 / 落款 / 成文日期 / 附件说明），列为：

| 中文字体 | 英数字体 | 字号 | 加粗 | 对齐 | 首行缩进 | 行距 | 段前 | 段后 |
|---|---|---|---|---|---|---|---|---|

页边距、页码、表格等参数本轮仍留在「高级设置」弹窗中。

#### 数据流：活链接 + 覆盖值

```
显示值 = 预设值 ⊕ 覆盖值
```

- 选择起始格式 → 参数表装载该格式的值，**覆盖值清空**
- 修改某一格 → **只记录该格为覆盖值，预设本身不变**（所以内置格式也能安全微调）
- 改动过的行：**行首色条亮起**（朱砂红 `#BC4B26`），行尾 `↺` 变为可点，
  格式区标题行汇总列出改了哪些字段（如「已改动：一级标题·加粗、正文·中文字体」）
- 点行尾 `↺` → 恢复**该行**；点「↺ 恢复全部」→ 清空所有覆盖值
- 「＋ 存为新格式」→ 把当前这套生效值存成一份新的用户格式，追加进左侧面板并滚到可见位置

**为什么不做成"选中即复制副本"**：那样每次微调内置格式都会污染用户配置；活链接能让用户
随时退回原始预设值，改动意图始终可见（哪几项被改过一目了然）。

#### 左列：预设面板

出厂只有 **4 个起始格式**（内置三个 + 「自定义格式」，后者默认选中），用户格式从空开始攒。

- 内层 `PresetOption` 行 + 外层**带边框的滚动面板**（1px `Theme.BORDER`）
- 面板尺寸固定 **215 × 400**，与右侧参数表（约 350px 高）接近；内容再多也不变，只在面板内滚
- **没有展开/收起按钮** —— 边框加滚动条本身已足够表达「这里还有更多」，再加按钮是重复设计
- 没有用户格式时显示空状态提示（「还没有保存过格式 / 改好参数后点上方＋存为新格式」）
- 用户格式名超过 8 字**截断显示**（`CUSTOM_NAME_MAX_CHARS`），避免撑宽面板

> 原型实现中踩过的四个 Tk 陷阱（`pack_propagate` 连带锁高、`wraplength` 不约束最小宽度、
> canvas 默认宽 378px 与默认 `highlightthickness=2`、滚动条 12px 会加到面板宽），
> 详见 [`../prototype/README.md`](../prototype/README.md)。正式实现会重写这套布局，
> 但**同样的陷阱会再踩一次**，值得先读。

#### 格式区可折叠

点「▾ 文档格式」标题即收起整块参数表，**摘要行仍留在标题旁**（所以折叠后仍能看到
「当前格式：X · 已改 N 项」），一屏内可见「开始处理」。折叠状态**不记忆**，每次启动都是展开。

## 5. 配置迁移策略

| 场景 | 处理 |
|---|---|
| 全新安装 | `_make_empty_config()` 产出 schema 3 + 注入内置项；`active_preset_id` 默认指向 `official`（与当前默认行为一致，不改变用户预期） |
| 已有 schema 2 配置 | 保留用户 `presets` 与 `active_preset_id` 不变，仅升级 `schema_version` 为 3 并注入内置项。**不丢设置** |
| 已有 v1.7.x 老配置 | 走现有 `_migrate_legacy_config()` 路径，先升到 2 再升到 3 |
| 内置项 id 冲突 | 用户预设用 uuid，内置用 'official'/'academic'/'legal'，天然不冲突；加载时若发现同名 uuid 项，以用户项优先并告警 |

**必须保证**：升级后用户原有的自定义预设全部保留、原有默认选中格式不变。这条要有测试兜底。

### 已定：覆盖值持久化（2026-02 定稿，P2 落地）

**结论：持久化，独立字段，字段级记录，字段名为 `preset_overrides`**（原建议名
`builtin_overrides`，因覆盖值对用户格式同样生效、key 可为 uuid，改名以免语义误导；
schema 仍为 3 —— 该字段尚无用户数据，改名无需迁移）。

```jsonc
{
  "schema_version": 3,
  "active_preset_id": "custom",
  "presets": [ /* 用户自建格式：uuid 完整快照 */ ],
  "preset_overrides": {
    // 字段级 delta：{预设 id: {键: {字段: 值}}}，键含元素名（title/body/…）
    // 与高级设置键（page/table/page_number_*），统一深合并语义
    "official": { "body": { "line_spacing": 30 } },
    "<用户格式 uuid>": { "title": { "font_cn": "楷体_GB2312" } }
  }
}
```

**模型**（与原型 `FormatState` 同构，对内置与用户格式统一成立）：

- `显示值 = 预设值 ⊕ 覆盖值`。改一格只记覆盖值，**预设本身不变**
  （内置的基准 = 代码里 `formatter.PRESETS` 的定义；用户格式的基准 = 它上次保存的完整 dict）。
- `↺ 恢复本行` = 删该键子树；`↺ 恢复全部` = 删 `preset_overrides[预设 id]`。
- **切换格式不清空覆盖值**：按 id 各存各的，切回 / 重启都还在
  （原型 `switch_preset` 会 clear，那是内存演示的简化，持久化语义下必须修正）。
- 「＋ 存为新格式」= 把当前生效值（基准⊕覆盖）存成新的用户格式（uuid 完整快照），
  自动选中新格式，并清空源格式的覆盖值条目（改动已折进新格式的完整 dict）。
- 格式化时 `生效 preset = 深合并(基准, preset_overrides[id])`，UI 显示与处理结果同源。
